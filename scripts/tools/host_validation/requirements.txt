# Core host-side Python dependencies for the maintainer host-validation
# runner (scripts/tools/host_validation/run.py) and the sample host suites it
# executes.  Supported interpreters: Python 3.10 and 3.12 (CI matrix);
# newer interpreters work when the same packages provide wheels.
#
# These are host test dependencies only: synthetic inputs, graph checks and
# numeric contracts.  No board SDK, no model frameworks.  The model-export
# frameworks the delivery plan declares optional on the host (torch, funasr,
# ultralytics) are deliberately NOT listed; suites that need them record an
# explicit optional-missing result instead of a fake pass.
#
# Version bounds follow the constraints the samples declare themselves
# (e.g. samples/vision/yoloe/conversion/requirements-host.txt,
# samples/vision/yoloe/evaluator/requirements-host.txt, the tracker pins
# in samples/vision/bytetrack/requirements-host.txt and the jsonschema
# pin in skills/requirements.txt).  lap/cython-bbox are the ByteTrack
# tracker's real CPU dependencies and jsonschema is what the skills
# evidence validators require (they refuse to auto-install it) — all
# three are mandatory core host dependencies, not optional extras.
#
# Tested versions (Python 3.12.14, macOS arm64 host, 2026-10-05 full-gate
# run): numpy 2.5.3, scipy 1.18.1, opencv-python-headless 4.14.0.94,
# PyYAML 6.0.3, onnx 1.23.1, onnxruntime 1.30.0, pycocotools 2.0.11,
# pillow 11.3.0, ftfy 6.3.1, regex 2026.9.29, lap 0.5.12, cython-bbox
# 0.1.5, jsonschema 4.26.0.  The YOLOE evaluator scoring path was
# additionally verified against pycocotools 2.0.10 (hermetic venv).
#
# scipy is split by environment marker: the 1.15.3 macOS arm64 wheel is
# unusable (standalone `import scipy.sparse.linalg` fails with a Mach-O
# __thread_bss zero-fill offset in PROPACK; fixed upstream by the 1.17
# PROPACK port to C, https://github.com/scipy/scipy/issues/25635), so
# Darwin on Python >= 3.12 must use >= 1.17.1.  SciPy 1.17 does not support
# Python 3.10, so Linux 3.10 legs keep the general >= 1.10 bound, where the
# 1.15 wheels are healthy (the failure is Darwin-specific).
#
# The opencv/pycocotools floors are the samples' own declared constraints
# (>= 4.8 / >= 2.0.7), not observed breakage records: the 2026-10-05 gate
# failures on opencv 4.12.0.88 (GoogLeNet/MobileOne) and pycocotools 2.0.10
# (YOLOE evaluator) were defects in the Zoo's own code — the legacy
# source-comparison fixtures rolled back the whole sys.modules table and
# evicted cv2 around the pinned load, and loadRes was fed a no-info
# document the evaluator's public contract never required.  Both are fixed
# in the samples with fresh-process regressions; upgrading either library
# was never the fix, and these floors do not claim it was.
