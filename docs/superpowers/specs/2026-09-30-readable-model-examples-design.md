# ResNet / YOLO 可读范例架构方案

日期：2026-09-30。状态：依据用户已确认的对话方案整理；未实施。
核对基线：develop，`eed26ce610d7fba03a68d1c0ee6e62603cd9b85d`。

## 1. 已确定的需求

- 首先服务用户自训练模型接入，其次服务现有模型的输入输出与业务改造。
- 先完成 ResNet、Ultralytics YOLO 范例；Python 为主，C++ 按需维护。
- 必须有简单的 `main.py` 和 `main()`：必要的参数处理、构造模型对象、调用 `predict()`、使用结果。
- 模型类包含初始化、前处理、推理、后处理和 `predict()`。用户打开一个任务文件，就能读懂完整流程。
- 不按函数机械拆文件，不引入通用插件框架，不新增 `rdk_zoo` 顶层包。
- 允许调整目录与接口，必须提供迁移说明。平台专用代码切片不是本轮目标。
- `platforms/` 历史副本最终移出活动分支，以 Git 历史保留。
- Codex 负责方案、任务派发与结果核对；代码实施和测试由 sz-dev 上 machao 用户的 Claude Code + GLM 完成。
- 不在本机安装或运行测试环境；ACT、Pi0 外部子仓库不在本轮范围。

本方案取代早先讨论中“每个前后处理函数独立成文件”和“新增 rdk_zoo 包”的提议。既有 X5/S 方案的来源追踪、精确目标检查、证据区分要求继续适用；冲突时以本轮用户已确认需求为准。

## 2. 现状与调整原则

YOLO 已有 `YoloDetect`、`predict()`、模型绑定与可注入 runner；保留这些已有能力，收敛 SDK 调用重复。ResNet 的 `classification.py` 当前是公共分类实现的再导出，需要增加可直接阅读的模型类流程。既有共享算法、解码器可继续使用，不能为了“完整文件”复制复杂算法。

完整流程可读，是指模型文件显式串起 preprocess、infer、postprocess；并不要求 SDK、NMS、张量绑定等所有实现都写入同一文件。已存在且合理的辅助模块不强制合并。

## 4. 模型类与入口

模型文件提供 `preprocess`、`infer`、`postprocess`、`predict`。`predict` 中直接写出三步调用，让主流程可见。已有 pre_process / forward / post_process 接口通过薄别名兼容，不维护两份实现。

`main.py` 的结构为：解析必要参数 → 创建模型对象 → `predict(source)` → 展示或保存结果。不得包含图像缩放、张量转换、SDK 加载、模型元信息绑定、NMS、坐标还原等业务。参数多不应成为另建多层启动框架的理由；确有复用的展示或准备功能可以沿用已有辅助函数。

`predict` 接收单张 BGR HWC 图像数组，或本地图片路径。路径读取错误必须指出路径；数组不得被原地修改。结果沿用已有结构化结果类型，预测默认不打印、不绘图、不写文件。CLI 的展示行为放在调用完成后。

图片路径支持只是输入便利层，不扩展视频、摄像头、异步或批量推理。ResNet 类使用现有分类配置与选择信息；YOLO 沿用现有任务配置、输出协议和结果类型，避免再造第二套配置体系。

模型对象重复 predict 时复用已加载模型。预处理产生的缩放/填充上下文按调用传递，不能因前后两张图片尺寸不同而复用错误变换。

## 5. 公共 Runtime

调用关系：`main.py → 模型类.predict → 模型类.infer → runner/薄 SDK 会话 → hbm_runtime`。

`samples/_shared/runtime.py` 只承接 SDK 导入、模型实例创建、获取原始元信息、执行推理和已有调度能力。真实硬件 Runtime 是板端安装的 SDK，该文件不是自研推理引擎。

首轮会话接口为 `RuntimeSession(model_path, *, target)`、`load()`、`run(inputs)` 及只读 `runtime` 属性。输入输出沿用 SDK 的原生映射，不在公共层猜测模型名称或输出语义。初始化保持延迟加载，load/run 时做实际目标检查；模型类及其 runner 负责把命名张量绑定到这个接口。SDK 适配不能依赖分类或 YOLO 的类型。

目前两类 Python 示例都调用 `hbm_runtime.HB_HBMRuntime`，先收敛实际相同操作，不人为拆出 X5/S 两个 Python backend。不设计假设 SDK 支持的 close/context manager；只使用已核实的资源释放能力。

已有其他模型继续通过原来的共享 runner 工作，ResNet、YOLO 先采用会话包装。禁止因此改变其他模型的导入或运行行为。已有调度功能必须保留其校验与不支持时的明确报错。

## 6. 目标、模型与协议

三者独立：目标板卡决定兼容性；模型文件决定加载对象；输入输出协议决定预处理绑定和后处理。

- 板端自动识别或显式指定目标，运行前核对实际板卡，不能用参数绕过检查。
- 主机查询、help、模型准备允许显式目标，不加载板端 SDK。
- 官方模型读取 `docs/release/{x5,s}/models.yaml`；板卡身份不代表所有模型都可用。
- 自定义模型以本地模型路径、已有模型配置类型和标签文件接入，不强制官方资产 ID，不新增统一描述文件框架。
- 配置携带 SDK 无法推断的语义，例如类别与输出协议；运行时张量名称、形状、类型与配置核验。
- 目标、输入布局、类别数、输出协议不匹配应明确报错，不回退到另一种解码器。
- 标签数按实际模型输出/配置检查；不能默认把所有自定义模型当成 ImageNet 或 COCO。

既有 YOLO DFL、LTRB、NMS-free 等协议保持独立；支持范围由实际绑定和导出流程决定，不能声称任意 Ultralytics 权重都能直接运行。

## 7. 导出、编译、文档

沿用 `权重 → ONNX → 目标工具链 → 板端模型` 的两个明确阶段。导出代码留在模型 conversion，平台工具链配置明确区分 X5/S；先整理实际文件和导航，不为展示目录而搬动全部配置。

每个范例提供三条路径：官方模型运行、自训练模型接入、修改前后处理/业务调用。自训练路径必须列明支持的网络/上游版本、权重格式、类别/标签、预处理、输出协议、实际编译配置、产物与 Runtime 参数的对应关系。

根 README 做模型/平台导航；模型 README 做上述路径导航；conversion 与 runtime 文档解释具体步骤；架构文档说明边界；AGENTS 引用同一套命令。中英文文档同步，不要求 Node、Catalog 或 Skill 才能执行推理。

Python 主线完整，现有 C++ 能力保留。仅在受本轮改动影响时调整 C++ 构建/引用，不启动全仓库 C++ backend 重构，不承诺跨板卡统一二进制。
