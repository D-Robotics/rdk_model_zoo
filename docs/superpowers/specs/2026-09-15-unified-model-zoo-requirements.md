# 全分支合并与 X3 重构：需求访谈记录

> 已整理为 [2026-09-16 完整 Spec](2026-09-16-unified-model-zoo-spec.md) 与配套实施计划。本文保留决策来源，不代表已实施。

状态：需求收敛中，非已批准的实现规格。工作基线：本地 develop / a282b36。本轮只设计需求，不执行全仓重构。

## 已确认的方向

- 保留两个仓库，仪表盘进入文档站；模型数据由源码仓库发布。
- 新开发最终在 main 统一维护，不因主力板卡变化而迁移整套源码或仪表盘；当前 develop 用于本地整合。
- 相同 Sample 面向用户提供一个入口，平台必要差异在内部表达；不以平台目录下复制整套 Sample 作为最终目标。
- 仓库需要面向 Agent 开发，承接用户指定对话中的七技能方案；已读取讨论正文，尚未取得或审查源码包附件。
- 最新要求：除分支全面合并，还要重新设计整体框架，并对 X3 做一轮重构。“雷克叉3”暂按 RDK X3 理解。
- 重构采用过渡兼容：统一新入口，允许内部重构；常用旧命令保留适配与迁移说明，不默认兼容全部内部 Python API。具体兼容清单、过渡期限和退出条件尚待确定。这取代此前将现有 Sample 框架尽量保持不变作为首要约束的做法，但不要求无收益的重写。
- 用户工作流优先级：Agent 辅助开发为主，普通用户不依赖 Agent 即可运行 Sample 是必须满足的基础体验。人和 Agent 使用同一套可执行工具，Skills 组织开发步骤；不能将 Agent 作为运行模型的必要依赖。
- 用户明确要求 less is more：不新增 sample.yaml；同样不以 agent.yaml 或其他文件名引入等价的独立执行描述。采用标准化 README、现有脚本与 Manifest，让人和 Agent 使用同一份事实来源。
- 用户进一步强调普通开发者的完整使用体验：保留根 README.md / README_cn.md、各级必要说明和 datasets；不使用 Agent 也能选择、准备、运行、开发和验证模型。less is more 减少重复与无收益的抽象，不删减基础文档、数据准备和既有功能。此前省略这些项目的结构图不是删除决定。
- 用户认可目录职责：samples、独立 datasets、docs、skills；公共运行代码放 samples/_shared，不预设顶层 utils/tools。随后针对 scripts 的质疑，已撤回固定顶层 scripts 的提案，用户要求继续据此设计。数据集不放 docs，Sample 内保留最小 test_data。现有仓库维护与发布工具清点后按实际需要安排，位置未定前保留现状；不为压缩目录删除功能。
- 2026-09-16 用户明确当前任务仅为合并框架与实施计划，并认可对“基于 X3 原始 C/C++ API 封装 hbm_runtime 常用接口子集”先做有限可行性验证、通过后推广的规划。它不等于 pyeasy_dnn 外面套一层，也不等于完整复刻 HBM SDK 或承诺 X3 可以加载 S 模型。完整 Spec 已将该工作列为独立决策门；当前不实施或板测。

## 已检查的现状

- 已完成 Ultralytics YOLO / YOLO26 的统一入口与任务分派；其他 Sample 尚未全面整合。
- X3 目录仍为 demos/classification、demos/detect、demos/Instance_Segmentation，包含 Python、Notebook、量化配置及文档。
- 多个 X3 目录内示例直接使用 hobot_dnn.pyeasy_dnn；不能假设其可直接替换为当前共用 YOLO 的 hbm_runtime。
- X3 目录中的 README 与若干文件仍含 X5 等平台内容。目录归属不能作为支持证明，需逐项核对硬件、编译资产与验证证据。
- 现有 YOLO 整合只证明这批任务的整合可行，不代表所有 Sample 都应套用同一基类。

## 访谈顺序

1. 重构深度与兼容边界：旧目录、命令、Python API、模型文件、Notebook 各需保留到什么程度。
2. 用户与 Agent 的核心工作流：选模型、运行示例、添加模型、量化编译、评测、发布与故障定位。
3. X3 支持范围与证据：迁移全部历史内容还是经验证的支持集合；板端环境和验收资源。
4. Sample、模型系列、任务、配置、资产的边界，及模型数量统计口径。
5. 共用组件与平台后端边界，Python/C++/Notebook 与工具链的维护策略。
6. 已验证 Skills 框架的位置、能力、输入输出和权限边界。
7. 版本发布、平台兼容矩阵、旧 tag 与下载兼容。
8. 分批迁移、回退办法、验收门槛及完成定义。

## 当前待决问题

Q1 已决：用户选择 A，统一新入口并提供过渡兼容，详见 ADR-0002。

Q2 已决：用户确认“Agent 辅助开发为主、开箱运行作为必须满足的基础体验”。批量转换和评测仍属于待设计能力，不因该优先级而被排除。详见 ADR-0003。

Q3 已定位：用户提供 ChatGPT 对话《开发RDK Model Zoo Skills》，已读取其最终方案及前序修订。来源：https://chatgpt.com/c/6aa24ec0-41f8-83ec-9b2e-4fb3e2f44f47 。当前取得的是对话正文，未取得源码包附件；不能将对话中的测试报告视为当前仓库已验证。

Q4 已决：用户选择 A，X3 以现有已发布能力为基线，完成全面梳理、重构、缺陷修复和验证。X5/S 独有模型向 X3 的新增适配不在本轮范围，单独规划。已发布能力仍需逐项核实来源与资产，不能以目录归属判断支持，也不能因验证暂缺而直接删除已发布能力。

Q5 已决：Python 为默认运行入口，保留已有 C/C++ 能力，是否新增双语言实现按 Sample 交付要求明确。用户明确要求 Notebook 全部移除：新主线不保留 .ipynb；迁移时将独有运行、转换与评测逻辑转为脚本，教学说明转为 Markdown，历史 Notebook 由旧 tag 保留。不为所有正式 Sample 强制补齐 C++。

Q6 已决：每个 Sample 提供自己的标准入口，Agent 通过清单定位；本轮不建设全仓总命令。入口风格统一，具体任务参数允许按能力不同；不能将本决定扩展为所有 Sample 必须采用 YOLO 参数。

Q7 已决：用户选择 A，默认在完整源码仓库中运行，各 Sample 引用集中维护的共用组件；本轮不要求单独复制一个 Sample 文件夹即可运行。完整源码不等于全部模型资产或全部环境依赖，模型与依赖按需获取。共用组件的具体组织方式尚未确定。

Q8 已决：用户要求修改目标平台后，必须在该平台实机上跑通基础 pipeline 并检查任务结果是否正常，例如修改 X3 就在 X3 执行并查看检测结果。本轮不要求完整数据集精度或性能测试；主机检查通过不能替代实机基础验证，也不能将基础验证表述为精度/性能达标。具体板卡连接、任务与规格覆盖另行落实。

Q9 已决：基础验证优先使用已有发布模型；修改导出、量化或编译流程时重新生成模型，并用新产物完成对应实机基础验证。兼容性边界：即使未修改转换脚本，若运行实现要求的输入输出协议已与现有资产不兼容，也不能直接复用旧模型宣称通过，必须对齐模型产物与运行实现后验证。未要求每次运行代码重构都重新量化。

Q10 已决：用户选择 A，按执行差异选择代表规格。基础板测覆盖受影响的平台、任务及不同输入输出协议；同一路径选择代表规格，其余规格进行清单、路径、配置与资产引用检查。分组依据应包括运行实现及模型元数据，不单凭型号名称；存在不同输入尺寸、输出布局、量化处理或独立分支时需要判断是否另设代表。验证记录仅声明实际覆盖的规格，不扩展为全部规格已板测。

Q11 已决：用户选择 A，统一源码版本并随版本发布平台支持与验证矩阵。每次发布对应一个仓库快照，不要求所有平台都发生更新；新增平台不改变主线和源码版本体系。Skills 保持独立版本线；模型资产不必随每次源码发布重新生成。历史平台 tag 保留。源码与 Skills 的具体 tag 命名、版本文件和 CI 触发规则尚需核对现有流程与 Hub 当前实现，不能直接沿用旧方案中裸 vX.Y.Z 专属于 Skills 的约定而产生冲突。

Q12 资源已确认：用户拥有全部目标板卡，X3、X5、S100、S100P、S600 均可用于验收。SSH 连接方式、Agent 执行权限、系统版本及具体测试目录尚未确认，执行前落实；拥有板卡不等于已连接或已完成环境检查。当前设计不按硬件缺失排除任何平台。

## 已确定的迁移验收原则

- 平台运行行为发生变化，必须在对应硬件上验证；其他平台或主机上的通过结果不能替代。
- 基础运行须实际贯通模型加载、输入处理、推理、后处理及结果输出，不能只检查退出码或模型能否加载。
- 检测任务需要查看结果是否正常；其他任务按自身输出语义验收，具体样例和判断办法在任务规范中明确，不统一套用检测图。
- 本轮不要求完整数据集精度测试、完整性能测试；保留既有 Benchmark 的历史来源，不用本轮基础验证替换或冒充重新测量结果。
- 优先用已有发布模型跑基础验证。转换流程变化时生成并测试新产物；模型协议不兼容时须先对齐，不能因为旧资产能够加载而忽略输入输出语义差异。
- 证据应明确源码提交、平台/环境、模型资产、输入、执行命令、运行日志及可检查结果。基础功能正常不等于精度与性能已经达标。
- 板卡不可用或基础结果异常时，记录未验证/失败，不将该平台的迁移标为验收完成。
- 每种受影响的平台、任务和执行协议采用代表规格板测；其他规格完成静态配置和资产引用检查。不同硬件平台不能仅因共用代码而互相替代板测证据。

## 承接既有 Skills 设计

以原对话最终的七技能方案为设计输入，不采用早期九技能草案：

| Skill | 职责 |
| --- | --- |
| rdk-model-zoo | 现成模型选择、版本化清单查询、Sample 运行 |
| rdk-model-zoo-repo | 识别目标仓库、提交、Sample 和适用规范 |
| rdk-model-zoo-integrate | 自有模型接入、输入输出与前后处理适配 |
| rdk-model-zoo-develop | 新增、维护、修复 Sample 和相关文档 |
| rdk-model-zoo-validate | 执行分范围验证并记录证据 |
| rdk-model-zoo-review | 完整 Sample 审计与差异评审，默认只读 |
| rdk-model-zoo-release | 模型与 Skills 各自的发布准备及一致性检查 |

- Model Zoo 专属 Skills 在模型仓库 skills/ 下维护；Agent 安装目录与维护源分开。Hub 是版本化分发入口，不手工维护第二份规则。
- 量化/编译复用外部 OE Skills。Model Zoo 定义所需模型接口，交出技术子任务，接收产物与原始证据，再完成 Sample 接入。
- 共享规则单源维护，但独立安装单个 Skill 必须具备所需参考资源。AGENTS.md 作为简短入口，不复制全部规范和模型清单。
- 复用现有 Manifest/Catalog；不在 Skills 内硬编码第二套 Benchmark 数值。
- 验证按平台、模型配置、任务、runtime、输入/数据集和检查类型划定范围；review 检查证据，不能替代 validate 的实际执行。
- 原方案中的 inspect_repo.py、read_catalog.py、validate_evidence.py 是只读辅助工具候选。对话报告 41 项工具/包结构测试通过、70 条 Agent 行为用例尚未执行；本轮均未复验。
