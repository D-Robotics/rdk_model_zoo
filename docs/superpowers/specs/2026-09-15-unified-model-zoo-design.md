# 统一 Model Zoo 架构设计

> 本文保留分节讨论过程。汇总评审稿为 [2026-09-16 完整 Spec](2026-09-16-unified-model-zoo-spec.md)，其中已纳入 X3 原生 C/C++ 兼容层的可行性决策；实现安排以其配套计划为准。

状态：分节讨论稿。需求依据为同目录 unified-model-zoo-requirements 文档；架构边界已获原则认可，第 2 节归并规则已获用户确认，接口建议仍待确认。

## 1. 已原则认可的架构边界

按职责共享公共能力，由 Sample 组织自己的任务流程。平台运行适配、资产获取和可证明通用的处理工具集中维护；模型特有解码、多模型调用关系和业务输入输出在 Sample 内维护。不建设强制所有任务继承的统一推理基类。

每个 Sample 保留 conversion / runtime / evaluator / model / test_data 等职责边界，提供标准入口，在完整源码仓库中运行。上述目录是否适用按实际交付能力说明，不用空目录冒充已实现能力。公共运行代码位置已确定为 samples/_shared/，具体模块和 API 仍需消费者审计。

## 2. Sample 归并规则（已确认）

- 同一部署流程在不同平台上的实现归入一个 Sample；平台支持由实际资产、实现与证据声明，不因为归并就扩展支持。
- 模型系列名不同不强制拆分 Sample；已有 YOLOv8 / YOLO26 可在一个入口下通过系列和任务选择不同协议。
- 相同任务不意味着属于同一个 Sample；独立模型家族或部署流程可以保留自己的入口，复用公共工具。
- 端到端运行需要多个模型组件时，以完整流程作为 Sample 的使用单位，组件资产分别记录。独立可用的组件仍可有自己的 Sample。
- 平台差异按实际位置保留：输入绑定与运行时放适配层，解码差异放相关任务模块，工具链差异放转换流程。若暂不能去重，允许 Sample 内保留有明确依据的平台模块，不另复制完整 Sample。

## 3. README、脚本与 Manifest（已确认）

遵循 less is more。不新增 sample.yaml、agent.yaml 或其他等价的每 Sample 执行配置，不要求 Agent 专属运行入口。此前的机器可读执行说明提案已撤回。

README 为人和 Agent 提供同一份操作说明，脚本完成执行，已有 Manifest 提供资产与 Benchmark 数据。Skills 引导 Agent 按需阅读目标 README、核对实际脚本、执行和审查结果。

普通开发者无需安装 Agent 或 Skills，即可完成模型选择、环境准备、数据准备、运行、修改与基础验证。根 README.md / README_cn.md 是首要入口，包含快速开始、平台支持、Sample 索引、数据集入口、文档站链接和开发说明；Agent 使用方法作为可选内容。分类、数据集、Sample 及必要子目录的 README 继续保留和维护。文档站承载仪表盘与详细手册，不替代检出源码时所需的本地操作说明。

README 至少让读者明确：

- 支持的平台、任务和模型，以及运行环境和必要依赖。
- 模型获取方式、工作目录、可直接复制执行的基础命令。
- 默认测试输入、输出位置和正常结果示例。
- 下载、安装和文件写入等需要理解的执行行为。
- 基础 pipeline 验证步骤、结果判断方法与已验证范围。

复杂任务的细节可继续放在对应 runtime、conversion、evaluator 说明中，通过链接访问；不把整套内容复制进顶层 README。运行、转换、评测仍可分别使用已有脚本，不强求同一个程序承担所有操作。

支持检查只增加实际有用的路径、链接、清单引用和入口回归检查；README 或配置结构完整不等于实际运行通过。

## 4. 目录职责（已认可）与公共代码整理

不预设顶层 utils/、tools/ 或 scripts/，将现有内容按实际职责审计，不整体改名搬入另一个杂项目录。公共运行代码归 samples/_shared/，数据准备脚本归对应 datasets/，Skill 专属脚本留在对应 Skill 内。仓库维护与发布工具尚需清点，位置未确定前保留现状，不删除功能。导入迁移和兼容需要结合消费者清单处理。

```text
rdk_model_zoo/
├── README.md / README_cn.md
├── AGENTS.md
├── samples/
│   ├── _shared/
│   ├── vision/
│   ├── speech/
│   └── ...
├── datasets/
├── docs/
└── skills/
```

此前预留顶层 scripts/ 的提案已撤回。datasets/ 独立保留，不能移入 docs/ 来减少目录数量。README 是普通开发者的第一入口，Skills 是可选能力。

- 多个 Sample 已使用且语义一致的能力，集中维护；修复后验证受影响消费者。
- 单个 Sample 专用的预处理、解码、组件调度继续留在 Sample 内。
- 同一 Sample 的平台运行时差异用少量明确模块隔离；跨 Sample 确有重复时再提取共用适配，不预先包装所有运行时 API。
- 归并需要输入输出、数值行为和默认参数证据。名称相同或功能描述相似不代表可直接替换。
- 不创建通用任务引擎、插件注册框架或强制推理基类；不为了目录对称补空实现。

保留版本/变更说明与现有必要项目文件。过渡期间旧 platforms 入口按兼容清单保留；分类优先沿用 vision、speech、robotics、llm、vla，分类调整仅在内容审计有依据时进行。结构图不是删除清单，现有 tros、CI、资源和子模块等内容须逐项核查归属，不能因未出现在示意图中直接移除。

### 数据集与测试输入

现有 X5/S 均有 datasets，仓库规范明确要求数据集说明和获取方式；新结构保留并归并这些内容。

- datasets/ 面向共用数据集，保存适用的样例数据、下载/准备脚本、目录约定和 README，包括来源、版本、获取条件及标签格式等必要说明。完整数据按需获取，不要求仅为运行一个 Sample 下载完整数据集。
- Sample 的 test_data/ 保留最小可运行输入和必要参考结果；通用大数据集由路径引用，不在每个 Sample 复制一份。
- 同名数据集是否去重需核对版本、子集、标注及预处理用途；标定与评测的差异须保留，不能只按目录名称覆盖。
- 本轮不要求完整精度/性能测试，不等于移除 evaluator、完整数据集获取方法或现有评测能力。
- 普通开发者通过 README 中的命令准备数据；Skills 读取相同说明，无额外 Agent 配置文件。

## 5. Sample 内部结构（细化建议）

沿用现有 main.py、run.sh 和模型实现文件的组织方式。以下为具备相应能力的 Sample 示意，不要求每个 Sample 创建所有目录：

```text
<sample>/
├── README.md / README_cn.md
├── runtime/
│   ├── python/
│   │   ├── main.py
│   │   ├── run.sh
│   │   └── <model>.py
│   └── cpp/                   # 有实际 C/C++ 交付时保留
├── model/                     # 模型获取脚本及说明
├── conversion/                # 已有导出、编译代码和配置
├── evaluator/                 # 已有评测入口
└── test_data/                 # 最小输入与必要参考结果
```

- main.py 是 Python 用户入口；run.sh 若保留，仅作为同一入口的便捷启动方式，避免重复实现任务选择和默认参数。
- 不额外引入 run.py、runner、pipeline 配置等同义层。任务专用参数仍由对应 Sample 定义，README 给出明确工作目录和完整命令。
- 平台选择在入口处明确，并将差异限制在模型资产、运行时调用和必要处理模块。平台存在不同编译或解码实现时保留相关文件，不复制完整 runtime/model/evaluator 目录树。
- 例如 X3 的 pyeasy_dnn 与 X5/S 的适用运行时可分别保留调用适配；YOLO 解码依据输出协议选择，不能直接按平台名称推定。只有跨 Sample 已证明共用的部分进入 samples/_shared/。
- 简单单任务 Sample 的处理逻辑可以留在一个模型实现文件中；YOLO 多任务、Paraformer 多组件等确有复杂度时按其任务或组件拆分，不要求所有 Sample 都有 preprocess.py、postprocess.py 或 backend.py。
- 现有有价值的验证测试保留；新增测试针对真实差异、回归风险和公共消费者，不为目录对称增加测试文件。
- 顶层 Sample README 说明用途、支持范围和最快运行路径；运行时、转换、评测内容较长时才分设子目录 README，通过链接组织，不重复整段说明。

### 多平台运行边界：以 YOLOv8 为例（源码核对后的设计建议）

2026-09-16 核对当前源码：

| 项目 | 旧 X3 目录的 YOLOv8 实现 | 当前共用 YOLO 实现 |
| --- | --- | --- |
| 加载与执行 | dnn.load 后调用模型 forward | HB_HBMRuntime 加载，model.run 执行 |
| 输出获取 | pyDNNTensor.buffer | 按模型名和输出名读取返回结果 |
| 元数据 | inputs/outputs 的 properties | 模型名称、输入输出名称及形状映射 |
| 反量化 | 框输出读取 properties.scale_data 并相乘 | 必须依据对应产物和运行时返回值判断，不能套用旧 X3 逻辑 |
| 解码假设 | 六输出固定索引，640 输入及三层网格存在硬编码 | 现有任务封装和输入适配依赖 HBM 风格对象 |

核对文件：platforms/x3/demos/detect/YOLOv8/YOLOv8_Detect.py，以及 samples/vision/ultralytics_yolo/runtime/python/yolo_runtime.py、yolo_detect.py。

特别注意：旧 X3 目录脚本的默认模型名含 bayese，不是 X3 支持证据。实施前须从已发布清单、下载来源和实机模型信息确定 X3 对应资产，不能照搬该默认路径。

建议按以下职责合并，不把 pyeasy_dnn 包装成虚假的 HB_HBMRuntime 对象：

1. 用户入口选择目标平台、任务和对应资产；使用不支持的组合时明确报错，不静默回退到其他平台模型。
2. 各运行时分别保留加载、输入绑定、执行、输出提取和必要元数据读取。仅选择目标实现后导入相应依赖；帮助和资产查询不依赖板端运行时。
3. 模型任务代码按实际协议映射输出角色、处理布局与量化，再执行相应解码。反量化责任明确，既不能遗漏也不能重复；不通过数组类型相同推断语义一致。
4. 在同一任务内尽量复用最终结果处理和绘制，例如检测框、分数、类别；这不要求原始张量接口跨模型完全相同。
5. 不支持的运行时特有参数明确提示，不伪装执行成功。公共代码提取后必须检查是否让 X3 被动依赖 hbm_runtime，或让其他平台依赖 pyeasy_dnn。

第一步在 YOLO Sample 内保留必要的运行时模块，具体文件名尚未定；经其他 Sample 复用验证后再将真正共用的部分提升到 samples/_shared/。先实现真实平台兼容，不预先设计通用运行时 SDK。

本节为设计与源码审计，不代表已完成 X3 接入或实机验证。后续 X3 验收使用正确发布资产，在板端完成输入到结果输出的基础流程，并检查检测结果是否正常。

## 6. 分批迁移与验收（建议组织方式）

在本文后续补充一份迁移表，记录旧路径、目标 Sample、实际支持平台、需保留的差异和基础验证状态，不再另外建设迁移数据库。每个 Sample 按同一顺序处理：

1. 核实既有能力和模型资产，识别重复实现及 Notebook 独有内容。
2. 合并 Sample，迁移必要脚本与说明，补旧命令适配。
3. 检查入口、引用、配置和受影响公共代码。
4. 在对应板卡用代表规格跑基础 pipeline，检查实际任务结果。
5. 保存命令、日志和结果证据，单独验收该 Sample；未通过的范围明确记录。

已有 YOLO 合并可复用源码审计结果，但其主机检查不能替代本轮要求的实机验收。模型仍优先采用现有发布资产，转换流程或模型协议改变时才重新生成对应模型。
