## 4. Sample 框架、代码整合点与具体调用关系

### 4.1 Sample 定义

Sample 是围绕一条完整模型部署流程组织的示例工程和维护单元，不等于一个模型文件，也不等于一颗芯片的 Demo。它可以包含多个相关变体、多个任务或多个协同模型，但必须能解释统一维护的依据。

“完整”指本来交付的部署流程完整；不要求每个 Sample 都新增训练、量化、C++ 或精度评估功能。默认支持完整源码检出，不承诺单目录复制即运行。

### 4.2 归并边界

沿用原稿：YOLOv8/YOLO26 在 `ultralytics_yolo` 维护；独立 YOLOv5 不混作 YOLOv5u；YOLO26 Depth 与检测分开。Paraformer 的多个 HBM 和 CPU 阶段组成一个流程，资产按组件记录。SigLIP 编码器不冒充完整图文应用，HIMLoco 离线动作推理不冒充机器人控制。[U1]

ResNet 多规格可以共用 Sample，但不合并权重身份或输入配置。OCR 组件流程、YOLOE 提示方式及旧 S 单独 YOLO 实现，未证明等价前保留局部独立模块。目录收敛与算法等价是两项验收，不能相互替代。

```text
└── tests/
```

`model_runner.py` 是本稿新增的明确职责名称：用于承载此前散在任务类中的模型加载和调用，并为任务层提供可替换的 Callable；不是新增厂商 SDK，也不是必须跨 Sample 统一的基类。若已有 `model.py` 已清楚承担相同职责，可沿用并在迁移表说明，不能为了模板再并存一套重复实现。其他小 Sample 可适当合并文件，但必须保留同样的依赖边界；YOLO 这种多任务 Sample 应使组合点能够独立定位。

不预建 `runtime/x5/`、`runtime/s100/`、`runtime/s100p/`、`runtime/s600/` 四套完整目录。局部 SDK 差异可以有专用函数，不因文件名不同就自动抽象成四个后端类。

### 4.4 各模块的职责与禁止事项

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `main.py` | 参数、目标与制品选择、前置检查、创建 Runner/任务对象、结果展示 | 下载地址数据库、DFL/NMS、内存管理、隐藏安装 |
| `model_binding.py` | 依据已知制品和实际元信息选择输入适配、输出适配、解码与处理策略 | 复制完整 Manifest、根据目录名猜芯片、执行任意配置命令 |
| `model_runner.py` | 延迟加载适用 Runtime、模型实例、元信息校验、调用适配器与一次模型执行 | COCO 业务逻辑、绘图、自动下载、任务参数解析 |
| `tensor_io.py` | 逻辑数据到 Runtime 数据打包、输出角色映射、布局处理、明确需要的反量化 | 猜测检测头、无依据乘 scale、NMS、原图坐标还原 |
| `yolo_detect.py` | 图像几何变换、调用 Runner、对应解码/筛选、坐标还原、返回检测结果 | 反复识别板卡、读取发布清单、每平台复制完整流程 |
| `decode.py` | 根据协议将模型语义输出变成候选检测；明确 sigmoid/softmax/objectness 责任 | 设备探测、SDK 加载、文件下载、隐藏平台默认值 |
| 展示函数 | 根据任务结果绘制或保存；可复用已有实现 | 再次执行模型或更改算法判定 |

只有 SDK 确实不同且需要局部处理时，Runner 才做薄适配；同一种实际调用接口不再套无意义的平台包装。`_shared/runtime/` 只在跨 Sample 真实消费者确认后建立。

### 4.5 创建阶段与推理阶段分离

创建阶段只执行一次：

```text
main.py
  → 解析参数（--help 在此退出，不加载 SDK）
  → 解析具体目标、模型/组件制品与已声明的契约
  → 确认本地文件和基础环境
  → model_runner.py 打开适用模型并读取实际元信息
  → model_binding.py 核对声明与元信息，生成本次 ModelBinding
  → Runner 保存输入/输出适配器
  → 构造 YoloDetect（注入 Runner、预处理规格与解码策略）
```

每次推理：

```text
YoloDetect.predict(image)
  → pre_process：几何处理 + 本次 ImageTransform
  → forward：调用同一个 Runner
       → tensor_io.pack_input（本次绑定的实现）
       → 系统 Runtime 执行
       → tensor_io.read_output（本次绑定的实现）
  → post_process：对应协议解码 + 必要筛选/NMS + 按 ImageTransform 还原
  → DetectionResult
  → main.py 或调用者显示/保存
```

平台和契约在初始化时解析；不能每帧读取板卡文件、重新解析全部 Manifest、重复加载模型或重新猜测输出类型。

### 4.6 X5/S 两条路径怎样真正汇合

下面是**条件性示例**，不表示所有 X5 或 S 制品都采用对应格式，也不声明任意两个制品数值相同：

| 项目 | 示例制品 A：X5 | 示例制品 B：某个已适配的 S 目标 |
| --- | --- | --- |
| 制品文件 | 已确认的 A | 已确认的 B |
| 输入接口 | 单输入 packed NV12 | 分开的 Y/UV 输入 |
| 输入适配 | `pack_nv12_single` | `pack_nv12_planes` |
| 输出适配 | A 的角色/布局映射 | B 的角色/布局映射 |
| 适配后输出 | 已确认的 DFL 语义张量 | 同一种已确认 DFL 语义张量 |
| 解码 | **同一份 `decode_dfl`** | **同一份 `decode_dfl`** |
| 任务流程 | **同一个 `YoloDetect`** | **同一个 `YoloDetect`** |

共用的单位是完整任务流程和已证实等价的算法；保留的差异是输入打包、张量读取及必要的执行配置。

如果另一个制品已经输出图内解码后的框，或使用不同的 NMS-free 协议，就绑定另一个解码/筛选策略，而不是强行还原成 DFL。共用入口不意味着所有模型走同一种数学过程。

### 4.7 模型绑定不是“Python 版 sample.yaml”

绑定是代码中的有限、可测试分派，不是可配置工作流引擎。

资产 ID、URL、摘要、目标声明继续由现有 Manifest 管理。输入输出契约可作为该 Manifest 的非执行元数据补充。绑定代码只将已知契约关联到实现函数，并维护必要的默认选择政策；不再保存一份全量模型规格表，不在代码与 YAML 两边重复 URL、Shape、类别和阈值。

不得在 Manifest 中增加 `command`、`shell`、任意 Python 导入路径、可执行表达式或流水线步骤。代码内也不得构造包含命令、下载地址和任意处理链的逐模型大配置字典来绕过 R08。

默认样例选择在一个明确函数中维护，只引用稳定制品 ID；README 从该行为给出命令，不手写第二套默认决策。资产事实可由单一数据源更新，但可执行行为的改变必须有代码审阅和测试。

### 4.8 多任务和多组件

检测、分割、姿态、分类可共享契约解析与实际一致的模型调用，但不统一成一个含大量任务条件的万能 `predict()`。任务入口由 `main.py` 一次选择，任务模块保持可单独学习和调用。

Paraformer、OCR、SAM 等多组件流程由本 Sample 的应用层串联各 Runner；每个组件拥有自己的制品、输入输出与必要的运行时。组件之间的 tokenizer、特征维度、精度或版本关系必须校验。不建设通用 DAG，也不能把各组件都能单独加载当成组合正确。

LLM 的 tokenizer/KV cache、策略模型的观测/动作状态、流式语音状态按实际任务单独定义。这里的单图 YOLO 接口不是全仓模型的强制接口。

### 4.9 如何证明完成了代码整合

每个试点提交必须提供源函数到目标函数的映射和至少三项维护场景：

| 场景 | 预期维护位置 |
| --- | --- |
| 修复相同 DFL 语义的解码缺陷 | 一处解码实现；验证所有实际受影响 X5/S 消费者 |
| 修复一种 NV12 打包错误 | 对应输入适配器；不复制或改写整条任务流程 |
| 接入同目标、同协议的新规格 | 新制品事实/引用与必要选择；不新增一份完整检测类 |
| 接入不同输出协议 | 新的局部协议实现及测试；不复制入口、下载和展示 |

只有“新目录存在”或“能够切换平台”不足以通过。代码行数下降不是硬指标；正确保留差异优先于盲目去重。两套必要的不等价实现必须有明确契约和理由，不能无说明永久保留几乎相同副本。

## 5. 公共代码、工程规范与数据集

### 5.1 两种共享不要混淆

**Sample 内跨平台共享**：例如 X5/S 使用同一份 YOLO 解码，仍放在 YOLO Sample 内。  
**跨 Sample 共享**：例如分类与检测确实使用相同的平台读取或制品校验，才进入 `samples/_shared/`。

公共模块至少有两个已识别的实际消费者，或在同一迁移批次中落地两个消费者。提取记录含输入输出、默认值差异、异常行为及影响测试。禁止把旧 `utils` 整体换名搬入，禁止公共模块反向导入具体 Sample。

平台注册表的读取、只读目标识别和 Manifest 访问应形成单一实现；在试点分类与 YOLO 共同需要它们时进入 `_shared`。具体文件名由已有代码收敛，例如 `_shared/platforms.py`、`_shared/assets.py`，不强制再建通用包体系。

### 5.2 Python 规范

| 编号 | 强制规则 | 验证方式 |
| --- | --- | --- |
| C01 | `main.py` 负责入口；不得堆入算法、下载策略和设备资源管理 | Review + 模块测试 |

## 6. X5/S Runtime、模型绑定与输入输出契约

### 6.1 五个必须分开的对象

| 对象 | 定义 | 不允许推导 |
| --- | --- | --- |
| Sample | 完整部署流程维护单元 | 一个 Sample 不等于所有芯片都支持 |
| Variant | 具体模型家族/规模/任务等语义身份 | 相同模型名不证明相同导出协议 |
| Artifact / Artifact set | 实际文件或已核定组件集合 | `.bin/.hbm` 后缀不证明兼容性 |
| Target profile | 具体板卡、所需环境与目标关系 | S100 结果不外推 S100P/S600 |
| I/O contract | 输入与输出角色、布局、数据语义及处理责任 | 相同 Runtime 名称不证明张量意义相同 |

本稿不填写未经核实的 SDK 最低版本、编译目标字符串、BPU 核数量或频率。平台名、SoC/编译目标与 Runtime 能力按 P0 实际证据建立映射。

### 6.2 目标选择与兼容性

程序接受明确目标或 `auto`。自动识别必须来自可信系统信息并能区分本期具体目标；未知值返回清楚诊断，不能按字符串中包含一个字母猜测型号。

准备/下载可在主机上选择任意已声明目标；本地执行需校验实机身份。显式目标与实机冲突时拒绝执行；未识别硬件的情况下不得把显式参数等同于硬件证据。必要的定制板手动覆盖属于单独、显式、记录证据的开发路径，不默认开放静默强制选项。

只声明可确认的兼容条件。不因版本更高、同属 S 系列或同为 `hbm_runtime` 就推断可用。必要字段未知时说明原因；阻止关键不匹配；对纯诊断缺项可以继续只读操作。

### 6.3 制品选择规则

官方制品以现有稳定 ID 选择，至少核对 Sample、任务、适用目标和必要组件。裸文件名不是全局唯一键。

自有模型使用显式本地路径及已知输入输出契约；能从元信息确认的结构字段可读取，无法从元信息确认的归一化、类别语义、解码方式和图内后处理必须由接入记录/调用者明确提供。未知契约不能“先试一种 YOLO 后处理”。

官方制品 ID 与本地覆盖路径同时使用时，只允许明确的本地缓存覆盖语义，并继续核对制品声明；本地不匹配文件不能继承官方已测状态。完全自有产物保持独立身份。

多组件集合必须核对组件角色和配套关系，包括必要的 tokenizer、标签、编码器/解码器接口及目标。禁止依赖“下载目录里碰巧已有哪个文件”选择版本。

### 6.4 目标接口：契约而非实现代码

以下名称用于规范 YOLO 试点的职责，可在保持含义的前提下对应现有类名；不承诺全仓统一接口或系统 SDK 已有同名方法。

| 接口 | 输入 → 输出 | 约束 |
| --- | --- | --- |
| `resolve_selection(...)` | 目标、任务、制品选择 → `ModelSelection` | 只读解析，不导入 SDK、不联网 |
| `build_runner(selection)` | 选择结果 → 可调用的模型对象 | 打开真实 Runtime，读取元信息并完成绑定 |
| `bind_model(selection, metadata)` | 声明 + 实际元信息 → `ModelBinding` | 验证式匹配；不猜测缺失算法语义 |
| `runner(prepared_input)` | 本任务规范化输入 → 本契约命名输出 | 只执行模型边界，不画图、不下载 |
| `pre_process(image)` | 应用输入 → 输入数据 + `ImageTransform` | 记录实际几何变换，不只记理论比例 |
| `forward(prepared_input)` | 输入 → 模型语义输出 | 调用被注入 Runner，任务层不直接识别平台 |
| `post_process(outputs, transform)` | 输出 + 变换记录 → `DetectionResult` | 根据已绑定协议处理，不按芯片猜算法 |
| `predict(image)` | 应用输入 → `DetectionResult` | 无文件副作用的可复用任务入口 |

`ModelSelection/ModelBinding/ImageTransform/DetectionResult` 是代码内的小型值对象，不要求新建全仓类型库、不序列化成配置、不通过反射装载任意处理链。单文件内足以表达时不强制另建 `types.py`。

### 6.5 ModelBinding 的内容和来源

| 信息 | 权威来源 | 绑定时处理 |
| --- | --- | --- |
| 制品 ID、来源、URL、可信 hash、目标声明 | 现有 Manifest | 读取，不复制到另一个运行清单 |
| task、输入/输出语义契约、组件角色 | 已审阅的发布元数据或自有模型接入记录 | 缺失时不能凭文件名补齐 |
| 输入输出名字、物理 Shape、SDK dtype 等 | 实际模型/Runtime 元信息 | 与声明核对，冲突拒绝 |
| 输入打包/输出整理/解码实现 | 当前 Sample 的代码 | 依据已知契约选有限实现 |
| 任务阈值、几何参数默认行为 | 一套文档化任务配置与兼容政策 | 可显式覆盖，不重复维护两套默认值 |
| 图内/图外处理责任 | 当前制品契约 | 确定 sigmoid、DFL、NMS 等是否已完成 |
| 本次参数、路径与实际环境 | 当前调用 | 进入运行记录，不回写发布事实 |

同一契约下若 Runtime 版本的输出表示变化，应增加经过校验的表示适配，不篡改已有契约的数值意义；如果模型语义真的变化，则采用新契约标识并保留旧解析。

### 6.6 Runtime 的实际使用

X5/S 优先直接使用其受支持的系统运行时。Runner 只是本 Sample 的稳定模型调用对象，不能覆盖系统模块、修改 `site-packages`、复制私有 SDK 或模拟并不存在的能力。

模型名称、输入输出属性、优先级与 BPU core 参数使用方式按实际已支持接口读取/调用。默认调度不无条件写死到所有目标；显式请求超出能力时报告不支持，不能吞掉参数后宣称已应用。

首次创建 Runner 加载模型；后续输入复用实例。首版不新增线程安全、并发、异步或零拷贝承诺；已有异步/并发交付保留专有路径，不能因“统一”而降级删除。不同 Runtime 的资源释放以真实 API 为准，不假称系统支持 `close()` 或上下文管理；项目自己的资源归属应有明确文档与错误清理测试。

### 6.7 输入：逻辑图像、传输数组与 SDK 存储分别定义

输入契约必须区别以下层次：

| 层次 | 内容 |
| --- | --- |
| 应用输入 | 例如 OpenCV BGR `uint8` 的 H×W×3；其他任务按各自数据定义 |
| 模型语义输入 | 模型实际要求的色彩、尺寸、归一化、布局和输入角色 |
| Runtime 传输数据 | 单路 packed NV12、分离平面、NCHW/NHWC 或多输入名字与数组 |
| SDK 物理存储 | 若本项目直接接触底层内存，核对对齐、stride 和生命周期 |

本稿为 YOLO 试点选择 OpenCV BGR 作为默认应用输入约定；若具体旧入口不同，兼容层需保留其已承诺语义，不因为高通 App 使用 RGB/Torch 就统一改写。模型需要何种颜色和数值范围由具体契约决定。

`ImageTransform` 至少记录原图尺寸、实际 resized 尺寸、左右上下 padding、实际 X/Y 缩放以及裁剪偏移（存在时）。舍入发生后的真实尺寸必须用于反向映射；不能在后处理重新根据理想比例估算。

NV12 的偶数尺寸、总字节数、连续性、平面形状和名字均须校验。示例函数 `pack_nv12_single/pack_nv12_planes` 按输入契约选，不按“所有 X5/S 必然如此”选。模型图已经包含的色彩或归一化处理不能在主机再次执行。

### 6.8 输出适配与量化责任

输出读取依据已核实的张量角色。优先使用可验证名字；SDK 只提供确定顺序时，使用有版本、数量、Shape 和 dtype 校验的显式位置映射。禁止不检查就取第 0 个输出并认为是框。

`tensor_io.py` 负责布局整理与明确需要的反量化。只能使用实际存在且意义已确认的量化参数；整数 dtype 不等于“需要乘 scale”，浮点 dtype 也不自动证明是最终概率。不得伪造 scale/zero-point，不能重复乘 scale。

图内输出已经做过 sigmoid、softmax、DFL、坐标解码或 NMS 时，契约分别注明；对应算法阶段跳过已完成部分，不用一个含糊的 `postprocessed=true` 覆盖所有操作。

适配后同一协议交付相同语义，例如“分类 logits”就不能在另一路径悄悄交付概率。只有到达相同语义边界后，才调用共享解码。

### 6.9 YOLO 检测的示例语义契约

以下是试点拟采用的**模型内部逻辑表示**，不是要求编译器改模型或要求 Runtime 原生返回这些 Shape。物理张量由适配器映射：

| 语义输出 | 约定 |
| --- | --- |
| 每尺度分类 logits | `[B, Hs, Ws, C]`，尚未 sigmoid；若制品交付概率则是另一个明确契约分支 |
| 每尺度框分布 | `[B, Hs, Ws, 4, R]`，明确 logits/已 softmax 状态 |
| stride、网格和坐标约定 | 与实际导出匹配；Hs/Ws 分别计算，不假设输入永远正方形 |
| 已解码候选 | `boxes_xyxy`、`scores`、`class_ids`，明确坐标系和是否已抑制 |

DFL 解码不硬编码输入 640、网格 80/40/20、类别 80 或回归通道数。参数来自有依据的绑定并与实际输出互相校验。必要的 sigmoid/softmax/objectness 合成各有一个责任位置。

NMS 策略为“无”“按类”“跨类”等明确值，来自当前模型/任务语义，不按平台自动决定；图内已 NMS 不再次执行。阈值默认保持该迁移入口承诺的历史行为，不能为了统一将 0.45 与 0.70 之类不同设置无声改成一个数。

逻辑表示不要求所有输出一律拷贝/全量展开。允许安全视图和无操作适配；明确生命周期。若为了统一会引入显著额外内存/时间，应保留局部高效路径并验证语义，而不是以架构整洁强行造成回归。本轮不宣称性能等价，发现明显退化需记录、定位并决定是否阻止推广。

### 6.10 DetectionResult 和其他任务结果

YOLO 检测公开结果至少包含：`boxes_xyxy` 为原图像素坐标的 N×4，`scores` 为 N 个已解释的最终置信值，`class_ids` 为 N 个类别索引。标签映射外置且有明确来源。空检测返回形状合法的空集合，不返回 `None`、伪框或混入错误状态。

当前任务结果在下一次推理后仍需可用，不能无说明暴露会被覆盖的 SDK 缓冲区。是否复制由实际生命周期决定，不默认承诺所有原始张量零拷贝。

分割、姿态、OBB、深度、编码器、语音、LLM、VLA 分别定义其有意义的返回契约，不统一成检测结果。应用流程返回数据；绘图、播放、保存等副作用由调用者显式发起。

### 6.11 用户执行契约

新规范化入口至少支持帮助、明确目标、模型选择、输入与输出路径；多任务 Sample 增加任务选择。下面是拟定的 YOLO 入口示例，尖括号项必须替换为真实已发布身份；其他已有入口可通过别名兼容：

```bash
python samples/vision/ultralytics_yolo/runtime/python/main.py --help
python samples/vision/ultralytics_yolo/runtime/python/main.py \
  --target x5 --task detect --asset-id '<已核定制品ID>' \
  --test-img './input.jpg' --img-save-path './result.jpg'
```

多制品 Sample 的新入口增加 `--list-models`，仅列出本 Sample 已登记的任务、制品和目标，可在无板端 SDK 的主机执行；它不是全仓 CLI。单制品 Sample 不为对称增加复杂筛选。模型获取脚本提供 `--dry-run`，只打印所需资源和目标位置，不实施下载。任一列表不得将“有资产”标成“已验证”。

`--target` 采用 `auto/x5/s100/s100p/s600`；实现时与既有平台注册 ID 建立明确别名，不改写历史 ID。`s` 仅用于筛选，不接受其作为本地执行目标。旧 `--model-path` 等参数按历史语义保留；自有模型路径缺少语义时必须显式选择已有契约或先完成接入。

README 的一键体验可以串联已有准备步骤，但步骤须可单独使用。新 `main.py` 的库导入和 `predict()` 不联网；缺少模型明确提示获取方法，不在失败分支静默安装或下载。旧脚本曾承诺自动下载时，过渡入口可保留并显式说明，不能把旧行为隐入新的纯推理接口。

帮助/列表/dry-run 不初始化 SDK、不建目录、不探测网络；执行所需输入或输出错误返回非零状态，错误参数与 Runtime 失败可分别用普通的参数错误/运行错误退出，不新增庞大错误码注册表。结果文件按本次调用确认生成，不能凭已有文件存在判成功。

用户传入相对路径相对于启动 cwd；内置资源从模块位置定位。默认输出位置在 README 中说明，不写入 `test_data/`。不得默认覆盖输入文件；目标输出已存在时按明确的拒绝/显式覆盖规则处理。旧兼容脚本单独保留其承诺的 cwd 和默认输出语义。

## 7. 模型资产、Manifest、Catalog 与来源一致性

### 7.1 数据目录与权威来源

沿用既有 `models.yaml`、`benchmarks.yaml`、Schema 和平台注册信息，收敛至 `docs/release/`。X5 与 S 可以分片，但其数据共同描述统一源码版本；`s` 分片内必须区分 S100/S100P/S600 的实际适用范围。

| 数据 | 权威位置 | 其他位置允许保存什么 |
| --- | --- | --- |
| 模型/变体/资产身份、下载地址、发布摘要、来源 | 对应平台的 `models.yaml` | 引用 ID 或经验证的生成快照，不维护第二份手写资源清单 |
| 设备目标、识别别名与已核定环境条件 | `platforms.json` | 读取结果，不在每个 Sample 复制设备映射 |
| 运行算法、输入输出适配及默认执行政策 | Sample 代码及相应契约说明 | README 解释其含义，Skills 指向该实现 |
| 历史 Benchmark 数值、条件和证据 | `benchmarks.yaml` 及其原始不可变来源 | Catalog 展示，不在页面代码填数 |
| 本次实测结论 | 对应验证报告与实际日志 | 发布清单引用范围，不用 URL 可下载代替测试 |
| 线上展示数据 | 已发布 Catalog 包 | 文档站锁定包身份和摘要 |

Manifest 读取不得依赖 Node 或网站 DOM。Python 运行/获取路径复用轻量读取能力；如果现有 YAML 解析器是运行所需依赖，在环境说明中明确。不得为避免安装解析器又手工维护一份完整 Python 资产字典。

C++ 不被强制加入 YAML 解析器；可保留显式模型路径与协议参数入口，并通过主机一致性测试关联 Manifest。不能为了默认路径在 C++ 另建一份不受校验的 URL/平台资产库。

### 7.2 本期允许补充的最小元数据

以下是**事实字段的设计语义**，在已有 Schema 中存在等价字段时复用，不并列创建同义字段。未知值不伪造：

| 信息 | 必要性与规则 |
| --- | --- |
| 稳定 asset ID 与 variant/Sample 关联 | 每个参与选择的实际文件可唯一定位；旧 ID 保持稳定 |
| `targets` 或既有等价字段 | 明确可用于哪些具体目标；不得只写含糊的“全部 S” |
| `io.input_contract` | 非执行的输入语义标识，关联已实现契约；不是 Python 函数路径 |
| `io.output_contract` | 非执行的输出语义标识，区分 logits/概率、不同检测头和图内处理范围 |
| 必要的输入输出角色与静态语义 | 只补 SDK 无法表达、运行确实需要且有来源的信息 |
| 组件角色、组件集合及关联版本 | 多模型流程防止错配；既有集合结构优先复用 |
| Runtime/编译环境条件 | 仅记录已核定的必要条件，未知不得填成任意最低版本 |
| 当前使用源码引用与历史测量来源 | 分开记录，不用一个 `source_ref` 同时代表两个时代 |

字段不得包含命令、表达式、任意函数导入名、安装步骤或图执行节点。转换工具链自身已有配置继续位于 `conversion/`，不是新的 Sample 编排配置。

首次引入必要字段时，以两个实际消费者验证：Sample 绑定可读取、发布器可解释。旧数据未提供字段时，旧阅读路径仍可展示，但不得自动承诺新 Runner 可安全执行。新执行范围中缺少必要事实是迁移缺口，不是填一个通用默认契约的理由。

### 7.3 ID 与目录不是同一件事

已公开 Sample/variant/asset/platform ID 默认稳定；目录重命名不自动改变 ID。确需合并时，记录 canonical ID、所有旧 ID、冲突理由和解析/跳转行为。

同名文件不等于同一资产；同一份已证明相同的文件也可以被多个流程引用，不因跨平台展示就复制文件身份。没有摘要时不能仅凭文件名或大小去重。

稳定 ID 的作用域必须明确：如果历史 ID 仅在平台内唯一，迁移后要保留可解析的平台限定引用或增加明确映射，不能把相同短 ID 无条件合并。

### 7.4 当前入口、历史证据与制品来源分开

```text
当前运行入口：统一源码提交/Tag + 新 Sample 路径
历史测量证据：原测量所在提交/Tag + 原文档路径/位置
实际模型制品：资产 ID + 原地址 + 已知摘要 + 编译/发布来源
本次验证记录：本次源码 + 实际环境 + 实际文件摘要 + 输入 + 结果
```

任何来源引用都要检查“版本与路径”的配对。不能只把旧路径换成新路径而保留旧版本，生成不存在的链接；也不能把旧 Benchmark 来源替换为新源码后声称重新实测。

历史 Tag 固定的是源码和其中的地址；缺少可信文件摘要时，不能证明远端 URL 中的字节始终不变。继续以 `null` 表达未记录可信摘要，并在本次使用记录中区分本地观测摘要与维护者确认的发布摘要。

### 7.5 下载与本地缓存

沿用 Sample 的模型获取入口并逐步复用真正公共的下载实现。下载列表从权威元数据解析，不在脚本再次手写一套 URL。

缓存至少按目标与制品身份隔离，示例可为 `model/<target>/<asset-id>/<filename>`；实际位置允许保持兼容，但同名跨目标文件不能互相覆盖。历史命令如要求旧位置，由薄兼容层映射，不复制算法或更改远端 URL。

先写临时文件，再验证并原子完成；中断或哈希不符不能留下看似完整的模型。只在有可信预期值时宣称完整性匹配；未知摘要明确提示未校验来源完整性。压缩包解包限制目标目录，不能信任包内路径越界；任何下载失败都不得自动换一个“相似模型”运行。

本稿不要求首次迁移重新下载所有资产。测试所使用的文件记录本地摘要和来源；未测试文件至少检查清单引用与获取逻辑，不把 HEAD 请求成功当成模型验证。

### 7.6 Catalog 发布及页面语义

发布器从固定源清单生成数据包。生成内容的路径或源码引用改变，payload checksum 可以正常改变；要求差异可解释、可重建、无意外丢失，不要求新数据保留旧校验值。

至少按稳定身份比较缺失、重复、归并、平台适用变化、资产 URL/hash、Benchmark 数值/单位/条件和证据指向。X3 历史来自固定旧来源，不参与新 X5/S 支持声明，也不自动从展示中消失。

文档站锁定内容包身份与校验，支持原路由到新模型页或历史页的明确跳转。People 页面与 Agent 读取清单看到同一份事实；“有资源”“已迁移”“某目标已基础验证”“有精度/性能数据”分开呈现，不用一个 `supported=true` 概括全部状态。

## 8. People / Agent 双重体验与七个 Skills

### 8.1 People 的完整路径

根 README 说明本期维护范围、入口及旧版本去向；Sample 索引按任务和平台帮助定位；Sample README 保留本地可执行信息，不仅链接到网站。

每个迁移后的 Sample README 至少说明：功能和边界、适用目标及已验证范围、环境与模型准备、最短运行命令、输入输出含义、结果位置、代码阅读入口、转换/评估能力和常见失败。双语文档中的命令、支持范围、参数及来源必须一致；不同语言不能对应不同默认行为。

一名不安装 Agent 的开发者应能依 README 完成一次基础运行，找到 `pre_process → forward → post_process`，并在自己的程序里取得实际任务结果。能够运行不等于能够理解，关键阶段不能被隐藏在不可追踪的注册器或自动生成巨型文件中。

### 8.2 Agent 的导航而非第二套实现

```text
AGENTS.md
  → 确认目标工作区、实际提交、未提交变更与用户权限
  → 加载适用 Skill
  → 阅读该工作区 Guidelines、Sample README、模型事实与代码
  → 在授权范围实施或只读分析
  → 调用与 People 相同的程序
  → 检查结果和适用范围
  → 提交带证据的交付或 Review
```

AGENTS 只保留简短路由、事实来源、维护命令和验证声明原则；不复制全部模型列表、平台版本与代码规范。Skill 安装源不是目标仓库，不能根据安装 Pack 的 Tag 推断用户当前代码或板卡。

### 8.3 七个 Skills 保持原命名与职责

| Skill | 主要输入与动作 | 交付 | 不能扩大到 |

### 8.4 源码目录、自包含与共享资源


### 8.5 工具链交接与安全边界

integrate 明确目标、实际 Runtime、源模型、输入输出职责、工作目录和验证预期；外部工具链返回产物、配置、日志和已做检查；integrate 再接入本次调用链；validate 验证接入后的结果，而不是沿用转换阶段的旧证据。

已有 X5 收据按实际格式读取；S 不假定具备同名字段或同一工作区布局。缺少信息记录为未提供。外部 Pack 管理目录不保存唯一源码、长期验证证据或用户原始数据。

README、源码、脚本、模型、数据和工具输出都是被处理的内容，不会自行扩大用户授权。运行 Sample 不包含刷写系统、替换 SDK、连接未知主机、上传私有模型或控制真实机械设备的许可。日志中隐藏凭据和不必要身份信息；诊断工具不执行报告里任意命令。

原稿提到的 `inspect_repo.py/read_catalog.py/validate_evidence.py` 先取得并审阅再复用，本稿不声称已有这些文件或其历史测试已通过。不建设新的执行代理或远端服务。

### 8.6 Skills 的代码兼容范围

未知工作区先只读识别；旧平台树、已统一 Sample、单 Skill 安装、外部模型和未完成迁移各有明确处理。不能让旧 Skills 按旧路径自动修改新仓库；也不能把新 Skills 的代码布局假设强加给历史版本。

## 9. 版本、发布、Hub 与 CI

### 9.1 发布对象

| 对象 | 标识 | 规则 |
| --- | --- | --- |
| 统一模型源码 | 根 `VERSION`；`model-vMAJOR.MINOR.PATCH` | 固定统一源码快照与 X5/S 支持/验证范围 |
| Skills Pack | `skills/VERSION`；`vMAJOR.MINOR.PATCH` | 与源码独立，满足当前 Hub 稳定 Tag 约束 |
| 单个 Skill | `SKILL.md` 内版本 | 按成员内容变化，不要求等于 Pack 版本 |
| 模型制品 | 既有 ID、URL、hash 与来源 | 源码发版不要求所有模型重编译 |
| Catalog | 既有内容标识与校验 | 随对应来源形成数据包，由文档站固定消费 |

Hub 注册文档在本次固定提交中要求规范稳定 `vMAJOR.MINOR.PATCH`，不能使用活动分支或预发布引用；本稿据此保留裸 `v*` 给 Skills，而非为了命名偏好修改 Hub。[H1]

首发具体版本在发布准备时检查已有 Tag、公共兼容变化和成员状态后确定。未执行版本检查，不填写真实可发布首发号。旧 `x5-v*`、`s-v*`、`x3-v*` 不改写；统一源码和 Skills Tag 都可能引用同仓提交，但所认证的发布对象不同。

### 9.2 独立版本的含义

Skills Tag 指向的仓库快照可能包含未单独发布的模型源码，因此消费者不能从 Skills Tag 推断那份模型源码已经完成模型验收。反之，模型 Tag 也不等于所有 Skills 已执行最新行为测试。

模型版本包含一个可重现主线快照，平台验证进度仍可不同。未变更、未重新实测的平台引用历史证据时须说明适用范围；受影响的运行行为不能直接沿用旧通过记录。统一版本不等于每次重新编译所有平台模型。

### 9.3 工作流边界

| 触发 | 执行 | 禁止 |
| --- | --- | --- |
| PR / 分批迁移 | 按影响执行主机、Schema、链接、相关构建与已要求的板端证据审查 | 仅凭文件移动绕过运行变化检查 |
| `model-v*` | 源码版本校验、模型/Benchmark 一致性、Catalog 包构建、发布范围检查 | 更新无关 Skills 版本或移动历史 Tag |
| Skills 稳定 `v*` | Pack/成员版本、自包含、单技能安装、辅助工具与行为结果检查 | 模型 Catalog 发布、改变模型 Latest |
| 文档站数据包更新 | 锁定来源与 hash、构建和路由测试 | 将“最新活动分支”当不可变数据源 |

前缀过滤之外，解析 Tag 后再次严格校验对象和规范版本。模型与 Skills 分开并发组及发布附件。Skills 发布明确关闭仓库 Latest 更新；发布器/安装器不得用全仓 `releases/latest` 判定某一种对象的最新版。

仓库级 UI Latest 如有维护规则，本期仅由模型正式发布设置；本规则不替代各对象自己的版本解析。模型与 Skills 的 PR 若同时修改共享资源，应运行实际受影响检查，不按发布标签或目录名跳过代码验证。

无需把全部板卡建设成常驻 CI runner；主机 CI 验证软件契约，实际板端运行记录按 §10 审阅。构建成功、下载成功、目录生成成功都不能写成模型全平台通过。

### 9.4 Hub 维护源切换

核实 Hub 当前 `rdk-model-zoo` 注册来源 → Model Zoo 仓库完成七技能准备并发布固定稳定 Tag → 在同一个 Hub 变更中移除旧注册、增加新维护源的七目录 → 检查目录唯一性、镜像、单技能安装与升级 → 旧源增加迁移说明。

原稿记载的旧 Device 来源须实际读取确认，不在未检查时执行删除。保持技能名，Review 为 `rdk-model-zoo-review`。Hub 镜像不手工修改内容，历史版本保留；若 Hub 安全检查拒绝大规模删除，按其流程审阅，不改脚本绕过保护。

### 9.5 生成物完整性

从拟发布提交的干净检出运行所有打包与发布检查。必要文件必须已在源码提交里，或由明确记录的可重现构建生成并随发布对象附带；Hub 单目录所需文件必须已进入 Tag。

验证所交付对象，而不仅是开发环境：只读清单检查不能借助未提交本地文件；Skills 安装不能借助工作区兄弟目录；Sample 在干净检出不能依赖旧平台树中未记录的软链接。源码 Tag 不自行包含子模块内容，README 必须给出精确初始化路径和失败提示，不宣称普通 zip 天然带全组件。

## 10. 验证矩阵、回归依据和证据规则

### 10.1 验证层次

| 层次 | 证明 | 不能证明 |
| --- | --- | --- |
| 静态/数据检查 | 路径、引用、Schema、ID、声明和旧路由一致 | 模型能够在板端运行 |
| 主机契约测试 | 绑定、前后处理、失败行为、入口依赖隔离 | 实际 BPU 执行正确 |
| 对应板端基础验证 | 指定目标/环境/制品的完整调用链结果 | 其他板卡、全体规格或全量精度性能 |
| 专项评估/性能 | 明确数据集与测量条件下的指标 | 未覆盖条件与机器人真实闭环安全 |

本期要求前 3 层的实际受影响范围，不要求新增第四层全覆盖。已有 evaluator 和性能能力保留，不能因为本期不全测而删除。

### 10.2 矩阵维度

以 **目标 × 任务 × Python/C++ 实际入口 × Runtime/环境 × 输入输出契约 × 代表规格** 建立验证矩阵。不机械执行不存在的笛卡尔积；先从真实交付中选择。

X5、S100、S100P、S600 分别记结果。共享解码在四个目标中可能有相同主机测试，但不能以 S100 板测替代 S100P/S600。新增非方形输入、量化表示、独立图内后处理、不同内存路径或组件组合时，需要新增相应代表。

同一协议选择代表规格后，其余规格至少检查制品关联、目标声明、尺寸与参数关系。没有运行的规格不标为“已上板”。维护支持声明和实测覆盖分别表达，不能为使矩阵全绿而删除原有能力条目。

### 10.3 主机最低验收用例

| ID | 用例 | 预期 |
| --- | --- | --- |
| H01 | 缺少 SDK 时 `--help` | 成功，无模型加载/联网/写入 |
| H02 | 导入任务与解码模块 | 不需要系统 Runtime，支持纯算法测试 |
| H03 | 根目录、Sample 目录、任意 cwd 启动 | 内置资源一致，用户相对路径规则一致 |
| H04 | 目标未知、显式目标与实机事实冲突 | 明确诊断，不回退为 X5/S 某默认目标 |
| H05 | 错任务、错制品、缺组件、未知契约 | 绑定失败，不先尝试推理 |
| H06 | 两种 NV12 输入契约 | 名称、dtype、平面/总字节、几何均正确 |
| H07 | 非方形输入与带 padding 图像 | 使用真实变换还原坐标，不硬编码 640 或正方形 |
| H08 | raw integer 与已转换输出 | 反量化恰好一次；缺少必要参数时失败 |
| H09 | 张量名字/顺序/Shape 变化 | 显式角色映射正确或拒绝，不误配分类与框 |
| H10 | logits/概率、DFL/已解码输出 | 不重复 sigmoid/softmax/解码 |
| H11 | NMS-free/图内 NMS/普通候选 | 仅按当前契约执行所需抑制，保留阈值语义 |
| H12 | 空结果与异常输入 | 空结果有合法形状；真正执行错误不伪装为空 |
| H13 | 同协议 A/B 适配输出的固定 fixture | 进入同一解码；结果匹配预先定义的参考 |
| H14 | 单任务选择 | 不导入无关任务的大型可选依赖 |
| H15 | download dry-run 与中断/哈希不符 | dry-run 无准备动作；失败不留下可用假文件 |
| H16 | 旧入口参数/默认值/cwd | 在承诺范围内行为一致，错误和退出状态可见 |
| H17 | 输出文件残留/同名输入 | 不误报成功，不默认覆盖输入 |
| H18 | Manifest 迁移与 Catalog 比较 | ID、资产、历史指标/证据及来源配对无意外变化 |
| H19 | 公共模块修改 | 列明并检查消费者，不单测公共模块就宣布完成 |
| H20 | 单 Skill 干净目录安装 | 不依赖未分发兄弟文件，不把旧通过数当本轮结果 |

H13 使用人工核定、旧实现导出或独立参考生成的 fixture。不能用被测函数先生成 expected，再以同一函数对比自己。模拟 Runtime 明确标注为测试替身，不代表任何 SDK 实测。

### 10.4 板端最低结果检查

| 任务 | 至少检查 |
| --- | --- |
| 分类 | 标签与索引、Top-K、固定输入参考及必要分值差异 |
| 检测/OBB | 框位置、类别、分数、角度与明显异常；审查结果图 |
| 分割/姿态 | 掩码/关键点与原图对齐、类别和维度、空结果 |
| OCR/语音 | 已知输入文字与关键中间阶段；多组件衔接 |
| 深度/编码器 | 尺寸、有限值、数值分布或固定参考；非空不是充分条件 |
| 策略/VLA | 观测与动作维度、有限值、离线参考；不触发真实执行器 |
| LLM/生成 | 小输入能完成，Tokenizer/状态/输出合理；不要求跨平台逐字一致 |

每个实际受影响的 C++ 交付增加构建及基础执行证据。若已存在特殊视频/多线程路径，本期改到它则单独选代表，不能拿静态图片的 Python 通过代替。

### 10.5 迁移前后对照

优先在**同一目标、相同实际模型文件、相同输入、相同参数和可比环境**下比较旧新链路。跨芯片制品的量化/导出可能不同，不以 X5 与 S 输出逐元素相同作为迁移要求。

对照顺序为预处理结果/变换 → 原始或明确转换后的模型输出 → 最终任务结果。只有进行了必要模型转换时，才把产物变化作为单独变量记录。

比较指标与容差在观察新结果之前写入测试或报告：确定性打包可按字节对照；纯布局整理可精确比对；浮点/量化差异有基于实际链路的容差；检测按匹配框、类别和分数比较；生成任务按已定义行为参考。不存在一个适用于所有模型的通用阈值，本稿不编造它。

若旧基线本身失败或明显错误，保留事实并将修复作为显式行为变化；不能把错误固定为正确标准，也不能无记录更新 golden 数据消除回归。没有旧运行环境时仍可进行独立正确性检查，但需标明没有完成旧新等价对照。

### 10.6 证据最小内容

沿用可读 Markdown 报告链接日志/图像/结果，不新建复杂执行数据库。至少包含：

| 类别 | 字段 |
| --- | --- |
| 源码 | 源与目标完整提交；工作区是否有未提交变更及其补丁/摘要；相关子模块提交 |
| 环境 | 具体目标、OS/镜像、Runtime/必要库版本；不包含凭据 |
| 制品 | 实际文件或集合身份、来源、可信摘要情况、本次使用的本地文件摘要 |
| 输入 | 输入文件/数据版本及必要摘要、任务参数、阈值和固定随机性条件 |
| 执行 | cwd、实际命令、开始/结束信息、退出状态、日志位置 |
| 结果 | 本次结果文件、检查方法、旧新差异、必要截图或数值 |
| 结论 | `passed / failed / not-run / not-applicable`、验证层次与适用组合 |

本地计算摘要证明本次使用的字节身份，不证明官方来源可信；不能自动回填为已验证的官方 hash。`not-run` 与 `not-applicable` 不计为通过。无原始记录不能将“开发者记得跑过”补写为历史实测。

### 10.7 证据的适用期与变更影响

证据绑定实际源码和制品。之后若公共输入转换、Runner、输出适配或解码改变，先分析其消费者；受影响的旧结论不得无条件沿用。保留原报告，增补当前提交的必要检查，不能改写旧报告日期或结果。

纯文案变化不强制全仓板测；重命名产生路径影响需运行相应入口测试。数值语义或 Runtime 行为变化须进入板端验证。验证范围由实际影响决定，不由“只改几行”决定。

### 10.8 未满足项如何阻止误报完成

可分别记录“源码已归置”“主机契约已通过”“某目标板测已通过”；不能合并成含糊的“已迁移”。必要目标没有实机记录或仍有异常时，该项不满足最终运行验收，但不阻塞无依赖的其他 Sample 开发。

不得通过改 README 支持表、删清单或把失败改为 `not-applicable` 来完成本期目标。真实范围缩减需要独立决策、来源记录和发布说明，而不是执行 Agent 自行处理。

### 11.2 迁移记录必须可定位到代码

继续使用原有人工迁移表，不新增迁移数据库。每条记录至少包含：源仓库/完整提交/路径/关键符号，目标路径/关键符号，归并依据，保留的差异，目标/任务/制品/契约，公共消费者，兼容入口，验证要求和证据。

本期必须特别给出“旧 X5 函数和旧 S 函数分别进入哪一个新函数”，而不是只列目录箭头。对未证明等价的两份实现说明为什么暂时保留、怎样选择，以及后续合并需要什么证据。

不预填未读取源代码的逐函数结论；P0 输出真实映射后，才能确定批量迁移范围。

### 11.3 每批变更的原子性

每个可审阅变更包含使该批可用的源码、导入、资源路径、README、Manifest 引用、下载入口、测试和兼容层。原则上一个完整 Sample 或一个可以独立回退的公共模块为一个变更单，必要时包含相互依赖的小提交；不是硬性要求所有 Sample 只有一个 commit。

不能先移动所有源码，几周后才统一修清单或文档。任何被标为已完成的批次在干净检出中可按说明使用。回退公共模块时同时处理依赖其新接口的消费者，不能只 revert 一个文件造成组合状态损坏。

### 11.4 Git 历史与切换主线

P0 固定所有实际来源的完整 SHA，并记录集成起点；用户 worktree 可能已经包含部分合并成果，不能未经核验从公开分支重新覆盖。不能直接使用 `ours/theirs` 作为语义冲突解决策略，也不为了整齐重写已发布历史。

文件归置与算法修正尽量分开提交，以便观察差异；最终提交组合仍满足原子可用。保留必要贡献来源、许可证和 gitlink。是否使用 merge 或分批迁入按实际祖先和工作树状态确定，不能假定原始分支可以快进。

迁移期间来源分支若仍接收修复，维护一份增量吸收记录，标明已检查到的源 SHA。主线切换前核对起点之后所有必要变更，明确哪些进入统一主线、哪些保留在历史版本维护中。

最终默认分支切换、保护规则、CI 触发、文档链接、安装指引和新 PR 目标一起审查；切换不删除历史分支。分支冻结或接收紧急补丁的规则由维护者在实施计划记录，不能默许两套主维护线无限并行。

### 11.5 并行开发边界

可并行处理互不重叠 Sample；共享模块、平台注册、发布清单公共结构、Schemas、GitHub 工作流由负责人串行整合。先约定契约版本再并行，不让每个 Agent 私自创造一套共享接口。

执行者交付变更和原始证据，主负责人独立验收。仅有 Agent 的“完成”文本不构成验证。发现范围外改动或未经授权的环境修改，应停止该路径并记录，不拿结果正确掩盖权限问题。

## 12. 兼容、回退与最终完成定义

### 12.1 两种迁移结果必须区分

| 类型 | 承诺 | 验收 |
| --- | --- | --- |
| 可执行兼容入口 | 原常用命令在已列明范围继续执行 | 参数、默认模型/阈值、cwd、输出位置、退出状态有测试 |
| 迁移说明入口 | 告知旧命令不再可执行，给出新位置 | 明确不兼容变更，不能统计为兼容通过 |

R10 中指定的常用命令默认属于第一类；不能由执行者擅自降为第二类。历史内部 Python import 不默认全部兼容，但本期作为 People 程序接口公开的新任务类和结果需在 README 定义承诺范围。

兼容层只补旧参数/路径和必要默认值，不能再维护另一套算法。新入口改了阈值或输出形状时，要么兼容层显式保持旧行为，要么记录公开不兼容并按版本规则发布。

### 12.2 过渡期限与退役条件

沿用原稿建议：至少覆盖首个统一正式版及其后一个次版本。达到期限不自动删除；还须确认迁移说明、引用清理、所需目标验收、预告和审阅完成。该期限是本稿建议，执行时不能当作当前删除授权。

历史 Tag、资产 URL 和证据不随入口退役改变。固定外部子模块不因本仓库退役目录而私自重写；移动 gitlink 时更新 `.gitmodules`、初始化说明和引用并核验同一提交。

### 12.3 回退方式

源码通过分批提交的可解释反向变更回退，不强推历史；模型回退到已存在明确身份的文件/集合，不覆盖旧 URL 的不同字节；Catalog 回退到原锁定包，不篡改 hash；Hub 回退到已有稳定 Tag，并保持唯一维护源。

涉及代码与数据的变更同时定义组合回退，防止旧代码读取新契约或新代码误读旧元数据。某个目标回退不自动声明其他目标同样验证过。主线回退后的发布仍使用新版本说明修正，不移动已经对外发布的 Tag。
