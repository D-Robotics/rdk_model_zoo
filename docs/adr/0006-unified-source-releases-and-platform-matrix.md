# 统一源码发版，以平台矩阵声明支持与验证范围

状态：accepted，用户在 Q11 选择方案 A。2026-10-05 补充裁定见文末。

合并后的源码采用统一版本，每个发布指向确定的仓库快照，并声明各平台的支持和验证范围；不再为新开发分别维护 X3、X5、S 的源码发布版本线。这样新增板卡或主力板卡变化不需要重组主线和版本体系，同时各平台可以在不同版本中按需更新。

Skills 独立发版，模型资产按需要更新，均不要求随每次源码发版重新生成。保留既有历史 tag 与模型来源。平台矩阵必须区分支持声明与实际验证范围，不能将一个平台、任务或代表规格通过扩大为所有配置通过。

具体 tag 命名及 CI 隔离尚未确定：旧 Skills 方案对裸 vX.Y.Z 的使用需要与统一源码版本协调，并在实施前核对 Hub 当前约束。

## 2026-10-05 补充裁定（tag 命名与版本线协调）

原“尚未确定”项裁定如下，实施记录见
[统一源码发布候选](../releases/unified-source-release.md)：

- **统一源码 tag 一律 `zoo-vX.Y.Z`**（首个候选 `zoo-v2.0.0`，对应仓库根 `VERSION`
  2.0.0，截至该记录未创建）。`zoo-` 前缀避免与任何既有发布线冲突。
- **`x5-v*` / `s-v*` / `x3-v*` 前缀保留给历史平台制品线**，其 tag 永不移动；平台
  制品版本继续由 `docs/release/{x5,s}/VERSION` 及其清单各自推进。
- **Skills 包沿用其自身独立的版本体系**（Pack 与成员版本见 `skills/pack.json`）：
  源码发版不重标 Skills、不改变其源码与分发；裸 `vX.Y.Z` 形态继续由 Skills 体系
  自行约束，与 `zoo-v*` 互不占用。
- **CI 隔离**：`develop`、`main` 与 PR 对同一组门禁（host-validation、sample-contract、
  model-catalog-data）等价触发；Catalog 工作树产物链接绑定生成时的完整提交
  （`link_ref: "HEAD"` 由加载器解析），不硬编码开发分支。
- 首个统一源码版本为候选状态：不打 tag、不建 Release、不切换默认分支；main 的
  提升与回退流程按上述发布候选记录执行。
